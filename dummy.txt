Inspect this repository before changing anything. I already have an IIS role and related Ansible modules/utilities. Treat the existing repository as the source of truth: follow its structure and conventions, reuse what is already there, and extend the current solution instead of creating a parallel role or duplicate modules.

Goal
Add an idempotent, one-time migration for a selected IIS site. Discover the site’s current settings, copy its content to configured D: paths while preserving ACLs, update IIS, and verify the service/site. The existing role already handles IIS installation, firewall setup, and baseline service configuration; integrate the migration into that flow.

First inspect and report:
1. Which existing roles, tasks, modules, utilities, variables, and tests relate to IIS installation, site discovery/configuration, Robocopy, backups, and service management.
2. Which can be reused or extended.
3. The smallest implementation plan that fits the repository.

Required behavior:
- The site name and desired content, log, and custom error-page paths must be variables, with suitable defaults and normal inventory/job-template overrides.
- Get the selected site’s current physical path, state, ID, log directory and rotation settings, and configured HTTP error mappings.
- Copy site content only while IIS still points to the old content path. Do not decide that migration is complete merely because the destination folder exists. If a previous copy was interrupted, allow a safe retry. Once IIS points to the desired D: path, later daily runs must skip Robocopy.
- Use the existing Robocopy utility/module if available. Copy recursively and preserve the source ACLs, including the root ACL. Do not use /MIR or /PURGE; leave destination-only content intact. Do not delete or modify the original C: content.
- Copy custom error-page files when their configured physical directory must move, then update only file-based error mappings to the new location. Preserve ExecuteURL and redirect mappings. Handle multiple error-page roots if the existing implementation supports them.
- Update the site physical path and IIS log directory only when they differ from the desired state. Preserve current log format and rotation settings unless explicitly overridden. Make copying historical IIS logs an optional variable; do not delete the old logs.
- Do not move or rename the overall C:\inetpub structure.
- Take a uniquely named IIS configuration backup before changing IIS settings. Take a post-change backup only after the service and site pass verification. Do not create backups on unchanged daily runs.
- Ensure W3SVC is configured to start and is running. Restart it only if IIS configuration actually changed. Verify the site is in the expected state after the change.
- Fail clearly if the source path or destination volume is unavailable, Robocopy fails, or post-change verification fails. Leave the source content and pre-change backup intact on failure. Follow an existing rollback pattern if the repo already has one; do not invent destructive cleanup.
- Keep the orchestration readable: put configurable values in the role defaults, use a loop for copy items where that fits the existing style, and keep backup, configuration, restart, and verification steps explicit.
- Support Ansible check mode where practical. Make the Get operation read-only, and have the Set operation report changed only when it actually changes IIS configuration.

Acceptance criteria:
- First run migrates the selected site and updates IIS.
- A second run reports no migration/configuration changes and does not run Robocopy or create backups.
- If a copy is interrupted before IIS is updated, a subsequent run can resume safely.
- Existing destination-only files and the original source remain untouched.
- Existing repo linting/tests pass; add focused tests following the repo’s patterns.

Implement the smallest complete change. Before finishing, summarize the files changed, the run sequence, assumptions about the existing module outputs, and the checks/tests performed.
