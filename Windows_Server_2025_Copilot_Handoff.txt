3. Two catalog capabilities

A. Readiness assessment
The consumer can request a precheck and receive a report before booking an upgrade. This request never automatically starts installation, removes agents or progresses into an upgrade.

Aria makes approved Server 2025 Setup sources available through an existing live attachment or staging path. The assessment job collects evidence and runs the actual Setup compatibility scan.

B. Upgrade
A separate request executes the controlled upgrade after readiness is established. The upgrade job repeats critical checks because an earlier assessment can become stale.

4. Agreed upgrade sequence

- Confirm assessment freshness, required evidence, maintenance coordination and workload drain where applicable. Pause conflicting patching or scheduled desired-state activity.
- Aria gracefully shuts down the VM and confirms it is powered off.
- Aria takes the powered-off snapshot, records its identity, attaches the approved ISO and powers on into the existing Windows installation. We launch Setup inside Windows; this is not booting into a clean installation.
- Aria starts our upgrade job when guest connectivity is ready.
- Ansible repeats critical checks and refuses installation if required evidence is missing or blockers remain.
- Prepare approved Tools updates and any ordinary prerequisites/reboots before Setup. Stage and verify all local recovery assets.
- Perform required agent offboarding/removal only within the authorized upgrade execution.
- Start Setup through durable local execution that survives loss of WinRM/PSRP.
- Windows completes multiple restarts. The prepared local SYSTEM worker handles post-Setup NIC/Tools recovery without requiring network access.
- AAP observes the attempt, reconnects and validates the target OS, Setup completion, recovery and required agents/workloads.
- Aria completes any required VM guest OS setting change and associated power cycle, then confirms connectivity again.
- Run the approved 2025 desired-state/hardening policy in check mode and report the proposed changes.
- Apply the approved policy through the existing change process, then validate connectivity, agents, workloads and desired state again.
- Publish the outcome. Aria handles ISO detachment and snapshot retention/cleanup under the agreed rules.

5. Assessment and execution guards

Assess:
- Source OS, edition, language, installation type and supported target choice.
- Approved media/image identity, integrity, licensing and activation approach.
- Required free space, pending reboot, relevant guest health and existing Setup activity.
- Current remoting and compatibility with the intended 2025 transport/hardening.
- Installed roles and applications, their target support and owner-provided smoke tests.
- Tools/NIC packages and offline prerequisites.
- Installed agent versions, deployment models, health and management connections.
- Backup evidence and VMware context supplied through existing processes.
- Approved 2025 policy revision and exceptions.
- Actual Windows Setup ScanOnly results and diagnostic logs.

Ansible check mode alone is not an OS upgrade compatibility assessment. Setup ScanOnly is a real diagnostic operation that writes temporary files/logs without completing installation. Interpret its documented exit codes explicitly; 0xC1900210 indicates no compatibility concerns.

Return READY, READY_WITH_WARNINGS, BLOCKED or INCOMPLETE. Record observed value, requirement, action and owner for each finding. Missing evidence and unreachable targets must be explicit.

Aria must inspect the assessment, not only AAP job success. Permit execution only after required checks pass and allowed warnings have recorded acceptance. Bind freshness to the host, target, media and policy.

6. Proposed Ansible structure and modules

Reuse the existing OS config repository and collection conventions.

Playbooks/jobs:
- Readiness assessment and reporting.
- Upgrade with preparation, recovery observation and validation.
- Existing desired-state job reused for preview and apply.

Role task groups:
precheck, guard, prepare, upgrade, wait, validate, report and rescue.

Proposed modules:
- win_upgrade_precheck: accepts target, media, policy and agent requirements; returns checks, blockers, warnings, scan interpretation, media identity, agent plan and readiness. It never starts installation.
- win_server_upgrade: prepare/start/status operations; accepts run ID, target, verified media and recovery settings; returns existing/new attempt, Setup progress, restart requirement, recovery state, observed OS and diagnostics.

Keep orchestration decisions visible in role tasks. Reuse existing modules and agent deployment roles where suitable. Keep VMware API operations out of the Windows role.

7. Durable execution and offline network recovery

The VMs use VMXNET3.

Before Setup, stage the approved Tools installer, all offline installer prerequisites, signed NIC driver files, worker, completion/rollback hooks and manifest under D:\OSUpgrade\<run_id>, or an approved persistent local volume. Verify integrity and protect the staging directory.

Register recovery before the upgrade as a local SYSTEM task. No network connection or interactive logon may be required to trigger recovery.

Use a short SetupComplete hook passed through PostOOBE to mark completion or arm the worker. Do not reboot inside SetupComplete.cmd. Any Tools reboot is controlled separately after Setup.

The worker must:
- Check the intended run ID, target OS and valid Setup completion condition.
- Use startup and periodic retries to accommodate delayed readiness.
- Repair the NIC only when needed and perform planned Tools maintenance.
- Persist progress and enforce bounded retries/reboots.
- Verify completion and disable itself afterward.

Follow the approved Tools path before and after the OS upgrade. Prevent upgradeAtPowerCycle from competing with controlled Windows/Tools maintenance. A migrated NIC driver may already work, but AAP must still verify recovery completion.

8. Waiting, reconnecting and retry behavior

Persist a stable upgrade run ID and local progress. Setup must continue independently of the remote session.

Model running, succeeded, rolled back, failed and unknown outcomes. Reachability alone is insufficient: a server might be between restarts, still completing Setup or back on the original OS.

If AAP or Aria observation is interrupted, observe the existing attempt before considering a new launch. Do not equate orchestration cancellation with termination of local Setup.

Do not immediately reboot after starting Setup. If NoReboot is used, it controls the first restart only; later restarts still need observation.

Timeouts must cover measured Setup, Tools recovery and reboot duration. Never automatically revert a snapshot merely because polling timed out.

9. Agent-specific handling

Azure Arc Connected Machine agent:
Retain a supported installation. Microsoft states an in-place OS upgrade should preserve the Arc connection without re-onboarding. Validate connectivity and required extensions afterward.

Defender for Endpoint on Server 2016:
Offboard and uninstall the separately installed MDE package before upgrading. Identify unified-sensor versus legacy MMA deployment before choosing the exact procedure. On 2025, use onboarding for its built-in components; do not reinstall the 2016 sensor package. This is distinct from uninstalling the Defender Antivirus feature.

Defender for Endpoint on Server 2019:
Retain the supported onboarded installation. Microsoft supports OS upgrades on 2019 and later. Validate endpoint health and fresh portal reporting afterward.

Tenable Nessus Agent:
Tenable does not support upgrading the host OS with its agent installed and directs reinstall/relink afterward. Our approach is approved removal before Setup, followed by a supported installation and relink on 2025. Preserve required grouping/linking inputs and validate reporting/scanning.

ServiceNow ACC:
Retention is proposed, subject to version-specific OS-upgrade support confirmation and pilot evidence. Check the agent/framework and content versions. ACC Monitoring 3.16.1 addresses PRB1968533 involving Server 2025 checks and WMIC deprecation. Validate fresh check-in and real collection; follow applicable re-registration handling if reinstalling.

Use existing deployment roles for agent actions. Keep secrets in credential stores and coordinate automatic redeployment policies. Restore required security coverage promptly. A running service alone does not prove the agent is healthy or registered.

11. Reporting and Aria handoff

Generate a consumer-readable HTML report plus compact structured results.

Include request/run/host identity, source/target OS, phase, readiness, OS outcome, recovery and agent results, blockers/warnings, unassessed checks, actions/owners, timestamps and diagnostic/report references.

Extend the existing job handoff with the required fields. Publish structured values through set_stats/job artifacts, with unique host keys and per_host false. Artifacts carry data and report references, not report files. Use the existing approved destination for detailed evidence.

Notification options:
- Recommended: Windows automation produces the report; Aria sends it through the existing consumer notification route.
- Alternative: Aria passes approved recipient/context variables; an Ansible reporting task sends it through the existing mail route.
- Existing Controller notifications may cover basic job events.

Choose one notification owner. Report blocked/incomplete results too. If artifacts are missing after cancellation, report incomplete assessment or unknown upgrade outcome. Retry notification independently; an email failure must never rerun Setup.

12. Failure handling and acceptance

Blocked/incomplete assessment: report and stop before agent removal/installation.
Setup rollback: retain diagnostics and restore required agent coverage on the actual source OS.
Recovery/agent failure: hold completion and retry the failed stage without relaunching Setup.
Policy/workload failure: hold handback and snapshot cleanup pending resolution or the agreed rollback decision.

Snapshots complement recoverable backup. VM rollback does not undo external application transactions or cloud-agent registration changes. Revalidate restored OS, security coverage and management check-ins.

Pilot both source OS paths using representative workloads, CIS settings, VMXNET3 and deployed agents. Exercise blocked/incomplete assessment, WinRM loss, driver recovery, Tools reboot, interrupted observation, timeout and rollback handling.

Success requires the expected 2025 OS/edition, completed Setup/recovery, working remoting, agent reporting, workload smoke tests and approved desired-state verification.
